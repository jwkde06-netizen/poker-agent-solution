# Project guidance

When changing the daily settlement UI, read `docs/daily-settlement-ui.md` first. Its compact worksheet layout is an explicit, repeated user requirement. Keep explanatory prose and processing history out of the default view. Preserve date-scoped cumulative player totals and verify them with `tests/daily-player-totals.cjs` when aggregation changes.

For game entry, keep current live-game boxes first, above the worksheet. Do not restore the stepper, explanatory text, scan diagnostics, or a date picker in the default header. Put scan/history/reservation tools in the overflow menu; historical date selection belongs in daily settlement. A scanned roster does not prove a game has started: show explicit `prepared` status as `시작 전` outside the live boxes, and include only identity-matched `active` records in those boxes. Do not infer running games from the highest game numbers. Preserve internal game number, physical table, and K홀덤 No. separately. Lifecycle changes must use the authenticated, version-checked handler and verify readback; never change sheet entries just to correct a status.

Direct-entry controls are also explicit user requirements: display the source reference simply as `No.`, give each game an end/start button, place undo beside New Game, and expand a compact game-format input row immediately under the live cards. Keep the agency column as text. Buy-in +/- must update the local count immediately, coalesce repeated clicks, and save through one serialized writer. Do not hide or falsely complete uncertain writes. Decrement/deletion must not require a typed reason. Undo must use journaled before-values with current-source/ownership guards; never overwrite subsequent manual edits. Validate queue failures/reconciliation and undo preservation with the dedicated counter-queue and backend undo tests, without changing production counts for testing.

Keep the logo and account control in one shared top bar, with navigation starting below it. In dark mode navigation labels/icons use white with a neutral active background. Game end/start and add-player controls share the same size and white background; use a drawn SVG undo arrow instead of a text glyph.

Game entry has a visible Scan button (the explicit camera-entry request overrides the earlier overflow-only scan placement). Desktop capture uses the webcam; mobile capture opens the native camera with file selection as a fallback. Scans reuse the accounting recognizer and independent chip verification, produce an editable draft, and only save after explicit game selection and review. No Telegram sends or automatic absence-based deletions. Existing-game scan totals never reduce recorded buy-ins. Game settings edits preserve player rows, date/formulas, and lifecycle metadata with source/version guards and verified readback. Test writes offline, never against production attendance.
